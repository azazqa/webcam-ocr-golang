## 1. 개요

### 1-1. 목적
일정 시간마다 화면이 전환되는 **문서를 띄운 모니터**를 USB 웹캠으로 비추고,
화면이 전환될 때마다 **이미지만 저장**하고(1단계), 이어서 저장된 이미지에서 **텍스트를 추출**한다(2단계).
두 단계는 하나의 프로그램 안에서 별개의 작업으로 실행된다.

### 1-2. 고정 조건

| 항목 | 결정 |
|---|---|
| 개발 환경 | WSL2 (Ubuntu 24.04) |
| 언어 | Go (`CGO_ENABLED=0`) |
| 실행 환경 | Windows 11, `.exe` |
| 카메라 | 일반 USB 웹캠 |
| 인식 대상 | 모니터에 표시된 인쇄체 문서 (한국어/영어) |

### 1-3. 결정 기록

| 항목 | 결정 | 이유 |
|---|---|---|
| 언어 | Go | WSL에서 Windows exe 크로스 빌드, 단일 exe 배포 |
| 영상 저장 | **하지 않음** | 필요한 것은 화면 전환 시점의 이미지뿐. 저장 공간 절약 |
| 이미지 추출 방식 | **화면 전환 감지만 사용** | 일정 간격 추출은 중복 이미지·추출 누락이 생길 수 있어 제외 |
| 저장 위치 | 추출 시작 전에 사용자가 설정 | |
| 저장 이미지 형식 | **PNG로 통일** (빠른 압축) | 형식 통일, 전처리 후 재저장 시 추가 손실 없음. 용량은 JPEG의 약 8~10배 |
| 프로그램 구성 | **하나로 통합** (`webcam-ocr.exe`), **CLI 사용 안 함** | 이미지 추출 → 텍스트 추출을 한 화면 흐름에서 이어서 진행 |
| 화면 전환 주기 | 2~5초마다 전환 (사용 환경) | 감지 기준값·무변화 시간 설정의 전제 |
| 텍스트 추출 시작 | **자동 실행 + 버튼 실행 둘 다 지원** | 자동 실행: 화면 변화가 설정 시간 이상 없으면 이미지 추출을 끝내고 텍스트 추출 시작 / 버튼 실행: [OCR 실행] 버튼 |
| 자동 실행 기본값 | **꺼짐**, 무변화 시간 **3분** | 화면 전환 주기(2~5초)보다 충분히 길게 |
| 수동 캡처 | **포함** | 자동 감지가 놓친 화면을 직접 저장 |
| 이미지 추출과 OCR | **별개 작업, 순서대로 연결** | 동시에 실행하지 않음. 이미지 추출이 끝나면 그 결과 폴더로 텍스트 추출을 이어서 진행. 두 작업의 연결 고리는 이미지 폴더 하나뿐 |
| GUI | walk | CGO 없음, 한글 표시, WSL 빌드 확인 |

### 1-4. 전체 구조

```
                          webcam-ocr.exe (프로그램 하나)
┌──────────────────────────────────────┐          ┌───────────────────────────────┐
│ 1단계: 이미지 추출 (작업 A)           │          │ 2단계: 텍스트 추출 (작업 B)    │
│                                      │          │                               │
│ 저장 위치 설정                        │          │ 이미지 폴더 (1단계 결과 자동)  │
│      ↓                               │ 추출 종료 │      ↓                        │
│ [USB 웹캠] → 화면 전환 감지           │ ───────→ │ (선택) 전처리                 │
│      ↓        (영상 저장 없음)        │ 결과 폴더 │      ↓                        │
│ 전환 시 PNG 저장 → 세션 폴더          │  넘김     │ OCR → txt, result.csv         │
└──────────────────────────────────────┘          └───────────────────────────────┘
```

- **별개 작업:** 작업 A와 B는 서로 호출하지 않고 동시에 실행하지 않는다. 연결 고리는 이미지 폴더 하나뿐이다.
- **이어서 진행:** 이미지 추출이 끝나면 2단계 화면으로 넘어가고, 방금 만든 세션 폴더가 입력으로 자동 지정된다.
  - 자동 실행: 화면 변화가 설정 시간 이상 없으면 → 이미지 추출 자동 종료 → 텍스트 추출 자동 시작
  - 버튼 실행: 사용자가 [추출 정지] → 2단계에서 [OCR 실행] 버튼으로 시작
- **단독 실행:** 2단계는 이전에 만든 세션 폴더나 다른 이미지 폴더를 직접 열어서 실행할 수도 있다.

## 3. 작업 A — 이미지 추출

### 3-1. 처리 흐름

```
저장 위치 설정 → 카메라·해상도 선택 → (모니터 영역·카메라 설정) → [추출 시작]
   → 프레임 수신 → 화면 전환 감지 → 안정되면 이미지 저장 + 로그 기록 → …
   → 종료: [추출 정지] 버튼 또는 자동 실행 조건(화면 변화 없음이 설정 시간 이상)
```

### 3-2. 저장 위치 설정
- 추출 시작 전에 저장 폴더를 반드시 지정한다 (폴더 선택 대화상자).
- 시작 시 확인: 폴더 쓰기 가능 여부, 남은 디스크 공간 표시.
- 실행마다 하위 폴더를 만든다: `<저장 위치>/YYYYMMDD_HHMMSS/`
- 마지막으로 사용한 저장 위치는 설정 파일에 기억한다.

### 3-3. 캡처 (구현 완료: `internal/camera`)
- 모든 COM/MF 호출은 **`runtime.LockOSThread`로 고정한 전용 고루틴 하나**에서 실행 (GUI의 STA 스레드와 충돌 방지)
- 지원 픽셀 형식: MJPG, YUY2, NV12, RGB24, RGB32 (H.264 전용 카메라는 미지원)
- DHT(허프만 테이블)가 없는 MJPEG 프레임 → 표준 테이블 자동 삽입
- `auto` 형식 선택: 최고 해상도 → 같은 해상도면 MJPG 우선 → 높은 fps
- 닫을 때 `IMFMediaSource.Shutdown()`을 호출해 카메라를 해제

### 3-4. 카메라 제어 (예정)
- 노출, 초점, 화이트밸런스, 게인, 밝기/대비: 수동 고정 + 설정 저장/복원
- IAMCameraControl / IAMVideoProcAmp 사용, 카메라별 지원 항목과 범위를 UI에 표시

### 3-5. 화면 전환 감지 (구현 완료: `internal/extract/scenechange.go`)

알고리즘:

1. ROI(모니터 영역) 잘라내기 → 박스 평균으로 작은 흑백 이미지 생성 (폭 320px)
2. 밝기 정규화 (평균 → 128): 자동 노출 변화와 깜빡임 무시
3. 변경 픽셀 비율 = 차이가 `PixelDelta`를 넘는 픽셀의 비율
   - **직전 프레임**과 비교 → 즉시 전환 감지
   - **`Lookback` 프레임 전(약 0.2초 전)**과 비교 → 페이드·슬라이드처럼 느린 전환 감지
   - 짧은 간격끼리만 비교하므로, 카메라 위치가 천천히 변하는 것(흔들림, 초점 변화)은 화면 변화로 보지 않음
4. 상태 판정
   - 두 비율 중 하나라도 > `ChangeRatio` → "변화 중"
   - 안정 조건을 연속으로 만족 → "안정"
5. 안정 구간 안에서 **가장 선명한 프레임**(평균 기울기 기준)을 저장
6. 마지막으로 저장한 화면과의 차이가 `DupRatio` 미만이면 중복 → 건너뜀
   - 비교할 때 위아래·좌우로 `MaxShift` 픽셀까지 어긋남을 허용 (카메라 흔들림 흡수)
7. 마지막으로 화면이 바뀐 시각을 기록 → 자동 실행의 무변화 시간 판정에 사용 (`LastChange()`)

매개변수:

| 매개변수 | 기본값 | 의미 |
|---|---|---|
| `AnalyzeWidth` | 320 | 분석 이미지 폭 (v0.7까지 160 → 글자가 뭉개져 전환이 작게 잡혀서 상향) |
| `ROI` | 전체 화면 | 감시할 영역 (모니터 영역) |
| `PixelDelta` | 25 | 픽셀별 차이 기준값 (0~255) |
| `ChangeRatio` | 0.01 | "변화 중"으로 볼 변경 픽셀 비율 |
| `StableDuration` | 300ms | 안정으로 판정할 최소 지속 시간 |
| `Lookback` | 200ms | 느린 전환 감지용 비교 간격 (타임스탬프 기준) |
| `MinStableFrames` | 3 | 저 fps에서도 안정 판정이 너무 빨라지지 않도록 하는 최소 프레임 수 |
| `DupRatio` | 0.02 | 마지막 저장 화면과 이 비율 미만으로 다르면 같은 화면 |
| `MaxShift` | 2 | 중복 판정 시 허용하는 어긋남 (분석 이미지 기준 픽셀, 1080p 기준 약 12픽셀) |
| `MinInterval` | 0 | 저장 간 최소 간격 |

- 수동 캡처 시 `MarkSaved(img, t)`로 마지막 저장 화면만 갱신 (`LastChange`는 유지)

알려진 한계:
- 손이 안정 판정 시간 이상 화면 위에서 완전히 멈추면 새 화면으로 오인할 수 있음 → 안정 판정 시간을 늘려 완화
- 커서보다 작은 변화(글자 한두 자 수정)는 의도적으로 무시
- 카메라가 크게 움직이거나 확대·축소되면(손 촬영) 같은 화면도 다르게 판정될 수 있음 → 웹캠은 **고정 설치** 전제
- 샘플은 휴대폰 손 촬영이므로, **고정 설치한 웹캠 영상으로 다시 확인**이 필요

### 3-6. 실시간 처리 성능
- 프레임마다 처리: 수신 → (MJPG) JPEG 디코딩 → 감지
- 1080p MJPEG 디코딩이 가장 무거운 단계 → 실제 PC에서 처리 fps 측정 필요
- 대응: 처리가 밀리면 최신 프레임만 처리하고 나머지는 버림 (감지는 초당 10~15프레임이면 충분하며, 시간 기준 안정 판정으로 fps 변동에 영향받지 않음)

### 3-7. 이미지 저장

- 저장 형식: **PNG로 통일** (모든 카메라 형식)
  - MJPG 카메라: JPEG 디코딩 → PNG (추가 손실 없음, OCR 결과는 JPEG 원본과 동일)
  - YUY2 / NV12 / RGB 카메라: 무압축 프레임 → PNG (완전 무손실)
- 압축 설정: Go `png.Encoder{CompressionLevel: png.BestSpeed}` (빠른 압축)
- PNG 저장은 감지 처리와 분리된 별도 고루틴에서 실행 → 감지 속도에 영향 없음
- 측정값 (1080p 문서 화면, 개발 환경 2코어 기준):

| 카메라 노이즈 | JPEG 원본 (참고) | PNG 기본 압축 | PNG 빠른 압축 (채택) |
|---|---|---|---|
| 없음 | 0.14MB | 0.22MB / 0.14초 | 0.26MB / 0.09초 |
| 약간 (±4) | 0.26MB | 2.05MB / 0.85초 | 2.58MB / 0.21초 |
| 보통 (±8) | 0.40MB | 3.08MB / 1.05초 | 3.59MB / 0.24초 |

- 예상 용량: 장당 약 2~4MB (이미지 300장 ≈ 1GB)
- 파일 이름: `0001_t00m12.40s.png` (순번 + 추출 시작 후 경과 시간)
- 추출 로그 `capture_log.csv`: 순번, 파일명, 촬영 시각, 경과 시간, 이전 화면 대비 변화율
- 실행 설정 `session.json`: 카메라, 해상도, 카메라 제어값, ROI, 감지 기준값

### 3-8. 수동 캡처 (확정)
- **[수동 캡처] 버튼**: 자동 감지가 놓친 화면을 사용자가 직접 저장
- 추출 중에만 사용 가능. 누른 시점의 최신 프레임을 PNG로 저장
- 순번·파일명 규칙은 자동 저장과 같고, `capture_log.csv`의 구분 열에 "수동"으로 기록
- 수동 저장 이미지도 중복 판정의 "마지막 저장 화면"으로 갱신 (같은 화면이 자동으로 다시 저장되지 않도록)

### 3-9. 추출 종료와 텍스트 추출 시작

| 방식 | 종료 조건 | 이후 동작 |
|---|---|---|
| **자동 실행** (설정에서 켜기/끄기, **기본 꺼짐**) | 마지막 화면 변화 이후 **무변화 시간**(설정값, **기본 3분**) 이상 화면이 바뀌지 않음 | 이미지 추출 자동 종료 → 2단계 탭 전환 → 텍스트 추출 **자동 시작** |
| **버튼 실행** | 사용자가 [추출 정지] 클릭 | 2단계 탭 전환, 세션 폴더 지정 → 사용자가 **[OCR 실행]** 클릭 |

- 자동 실행이 켜져 있어도 [추출 정지]와 [OCR 실행] 버튼은 항상 사용할 수 있다.
- "화면 변화"의 기준은 화면 전환 감지와 같다 (3-5). 커서 이동이나 센서 노이즈처럼 `ChangeRatio` 이하의 변화는 화면 변화로 보지 않는다.
- 무변화 시간 계산 시작점: 마지막으로 "변화 중" 상태가 끝난 시각. 추출 시작 후 한 번도 변화가 없으면 추출 시작 시각.
- **무변화 시간은 문서 화면 전환 간격보다 길게** 설정해야 한다. 짧으면 화면과 화면 사이에서 추출이 끝나 버린다 (사용 환경의 화면 전환 주기는 2~5초 → 기본값 3분은 충분히 김. 발표가 끝난 뒤 최대 3분 후에 자동 종료됨).
- 1단계 화면에 남은 시간을 표시한다 (예: "자동 종료까지 2분 42초").
- 무변화 시간 설정 범위: 10초 ~ 30분 (분·초 단위 입력).
- 저장된 이미지가 0장이면 텍스트 추출을 시작하지 않고 알린다.
- 손으로 화면을 가리는 등 일시적인 변화도 무변화 시간을 다시 계산하게 만든다 (자동 종료가 늦어질 뿐, 이미지가 잘못 저장되지는 않음).

## 4. 작업 B — 텍스트 추출 (OCR)

### 4-1. 처리 흐름

```
(1단계 종료 시) 세션 폴더 자동 지정 ─┐
(단독 실행 시) 이미지 폴더 직접 선택 ─┴→ 엔진·언어·전처리 (설정값 사용) → 시작 → 결과 확인·저장

시작: 자동 실행 (1단계가 무변화 시간 조건으로 끝난 경우) / [OCR 실행] 버튼
```

- 자동 실행 시 엔진·언어·전처리는 미리 저장된 설정값을 그대로 사용한다.

### 4-2. 입력
- 이미지 폴더(하위 폴더 미포함) 또는 이미지 파일 여러 개
- 지원 형식: jpg, png, bmp, tif
- 작업 A의 결과 폴더가 아니어도 처리 가능. `capture_log.csv`가 있으면 결과에 촬영 시각을 함께 기록

### 4-3. 전처리 (예정)

| 항목 | 방법 | 순수 Go |
|---|---|---|
| 원근 보정 | 모니터 모서리 4점 지정 → 4점 변환(8x8 연립방정식) + 양선형 보간 | ✅ |
| 흑백 / 대비 / 확대 / 약한 블러(모아레) | 직접 구현 | ✅ |
| 렌즈 왜곡 보정 (선택) | 측정: Python+OpenCV 체커보드로 1회 측정 → JSON / 적용: Go에서 재매핑 | 측정 △, 적용 ✅ |

- 4점 정보는 작업 A의 `session.json`(ROI)을 자동으로 불러오거나 2단계 화면에서 직접 지정

### 4-4. OCR 엔진 (구현 완료: `internal/ocr`)

```go
type Engine interface {
    Name() string
    Recognize(ctx context.Context, imagePath string) (string, error)
}
```

| 엔진 | 구현 | 비고 |
|---|---|---|
| `windows` (기본) | PowerShell 5.1 + `-EncodedCommand`(UTF-16LE Base64) → `Windows.Media.Ocr` | 설치 불필요, `ko` OCR 팩 필요, 호출마다 약 1초 추가 |
| `tesseract` | tesseract.exe를 내부에서 호출, `-l kor+eng --psm 3` | UB Mannheim 빌드 + kor 데이터 |

- Microsoft 문서는 Windows OCR을 "패키지 ID가 있는 데스크톱 앱에서 지원"으로 명시 → 패키지 없이 호출하는 방식은 **실제 PC에서 확인 필요**
- 개선 후보: PowerShell 없이 WinRT 직접 호출 (속도)

### 4-5. 출력
- 원본 이미지 폴더 안에 `ocr/` 하위 폴더 생성 (원본 이미지는 수정하지 않음)
  - `ocr/0001_t00m12.40s.txt` (UTF-8)
  - `ocr/result.csv` (순번, 파일명, 촬영 시각, 텍스트)
  - `ocr/result.json`
- 이미 처리한 이미지는 건너뛰기 옵션 (재실행 시 이어서 처리)

## 부록 A. 영상 형식 검토 (참고)

v0.4에서 영상 저장을 제외했으므로 현재 구현 대상은 아니다. 향후 영상 기록이 필요해질 경우를 위한 검토 결과다.

### A-1. 형식별 비교

용량은 1080p 30fps 기준 대략치이며 화질 설정과 화면 내용에 따라 크게 달라진다.

| 형식 | 압축 방식 | 용량 (대략) | 장점 | 단점 | Go(CGO 없이) 구현 |
|---|---|---|---|---|---|
| **MJPEG AVI** | 프레임마다 독립된 JPEG | 초당 3~8MB (시간당 10~30GB) | 구현 쉬움, 프레임 단위로 바로 꺼낼 수 있음, 카메라 MJPG를 재압축 없이 저장 | 용량이 매우 큼 | 쉬움 (icza/mjpeg) |
| **MP4 (H.264)** | 프레임 간 압축 (변한 부분만 저장) | 초당 0.3~1MB. 문서 화면처럼 거의 정지된 화면은 훨씬 작음 | 용량 작음, 어디서나 재생, 하드웨어 인코더 사용 가능 | 프레임 추출 시 디코딩 필요, 비정상 종료 시 파일이 깨짐(조각 MP4로 완화) | 중간 (MF Sink Writer COM 호출 직접 구현) |
| **MP4/MKV (H.265/HEVC)** | 프레임 간 압축, H.264보다 고효율 | H.264의 약 50~70% | 같은 화질에 더 작음 | 인코딩이 그래픽 하드웨어에 따라 다름, 재생에 HEVC 확장이 필요할 수 있음, 특허 문제 복잡 | 중간~어려움 |
| **MKV (H.264 등)** | 컨테이너 (코덱은 MP4와 동일) | MP4와 동일 | 비정상 종료에 강함, 자막·여러 트랙 지원 | 일부 편집 도구 호환성 낮음 | 어려움 (MKV 작성기 직접 구현) |
| **WebM (VP9 / AV1)** | 프레임 간 압축, 로열티 없음 | H.264보다 작음 | 특허 부담 없음 | 소프트웨어 인코딩 CPU 부담 큼, AV1 하드웨어 인코딩은 최신 그래픽 카드만 지원 | 어려움 |
| **무압축 AVI (YUY2/RGB)** | 압축 없음 | 초당 약 120MB 이상 | 무손실, 구현 단순 | 비현실적인 용량 | 쉬움 |
| **이미지 연속 저장 (JPEG/PNG)** | 프레임마다 파일 | MJPEG과 비슷 (PNG는 더 큼) | 구현 가장 쉬움, 바로 열람 | 파일 수가 매우 많음 | 쉬움 |

### A-2. 결론
- 영상 저장이 필요해지면 **MP4(H.264)**가 용량·호환성 면에서 가장 적합하다 (Windows Media Foundation의 하드웨어 인코더 사용).
- 구현 난이도만 보면 MJPEG AVI가 가장 쉽지만 용량 부담이 크다.
- 현재 방식(화면 전환 이미지만 저장)은 1회 추출에 이미지 수십~수백 장(PNG 장당 약 2~4MB) 수준으로, 영상 저장보다 저장 공간이 훨씬 적게 든다.
